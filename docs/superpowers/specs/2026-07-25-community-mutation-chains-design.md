# 方舟社区审核串联用例设计

## 目标

在“方舟社区发帖”项目中补充帖子、评论和用户资料审核的可执行接口用例。用例在一次运行内从前序响应提取业务 ID，并以该 ID 完成后续审核和状态验证。接口请求继续使用 CMS 加密协议，批量执行共享一次内存登录会话。

## 范围

纳入以下非删除接口：

- 帖子：`create_update_post`、`list_post`、`detail_post`、`pass_post`、`reject_post`。
- 评论：`add_post_comments`、`list_post_comments`、`pass_post_comments`、`reject_post_comments`、`reply_post_comments`。
- 用户资料审核：`list_member_update_log`、`pass_member_update_log`、`reject_member_update_log`。

不纳入任何删除接口或清理动作：`del_post`、`del_post_comments` 和 `del_member_update_log`。现有删除相关模板不新增为资产，也不在本轮运行中执行。

## 用例模型

每个资产是一条独立、完整的业务链，避免批次中不同用例依赖彼此的变量。

1. 帖子通过链：创建唯一前缀的待审核帖子，提取帖子 ID，查询列表和详情，审核通过，再查询详情确认状态为通过。
2. 帖子驳回链：创建另一条唯一前缀的待审核帖子，提取帖子 ID，审核驳回，再查询详情确认状态和驳回原因。
3. 评论通过与驳回链：各自创建自动化帖子和待审核评论，提取帖子与评论 ID，执行目标审核，再查询评论列表确认状态。回复链仅针对已通过评论执行。
4. 用户资料通过链：查询待审核资料修改记录，提取一个尚未在当前批次使用的记录 ID，通过审核，重新查询并确认目标状态。
5. 用户资料驳回链：同样查询另一条待审核记录，驳回并重新查询确认目标状态及拒绝原因。

用户资料审核不创建虚构记录，也不会选择非待审核记录。若当前环境的待审核记录少于两条，相关用例以明确的“前置数据不足”结论结束，并保存脱敏请求与解密后的业务响应作为证据。

## 写入授权与执行

- 所有创建、审核与回复步骤标记为 `mutating`；默认不允许执行。
- 执行中心增加批次级“允许业务写入”显式确认。未确认时，运行器在首个写步骤前安全拦截，不发出请求。
- 用户已授权本测试环境的业务写入；该授权仍需在页面或 API 调用中显式传递，不能改为全局默认开启。
- `CmsApiRunner` 对同一批次延迟登录一次并复用内存 Session。认证 Token 只保存在内存中，不进入变量、SQLite、报告或日志。

## 证据与报告

每个 API 步骤记录动作、HTTP 状态、业务状态、耗时、脱敏请求摘要和解密后的脱敏业务响应。失败时保留同等证据。报告按用例展示“创建或查询、动态 ID 提取、审核操作、二次验证”的步骤结论，区分接口异常、断言失败、写入未授权和前置数据不足。

密钥、密码、TOTP 秘钥、Token、加密原文、密文 `data` 与签名 `sign` 不能写入源代码、数据库、报告、测试夹具或 Git 提交。

## 测试与验收

- 单元测试：请求安全等级、动态变量插值、ID 提取、同批次 ID 去重、前置数据不足、授权拦截与状态断言。
- 集成测试：批量共享一次登录、写入授权传递、失败步骤证据脱敏、报告显示本地时间。
- 手工验证：在测试环境执行一条帖子链、一条评论链和可用的用户资料审核链，确认报告展示解密业务结果且不泄露敏感值。

## 非目标

- 不新增删除功能或自动清理策略。
- 不把登录 Token 作为可编辑或可提取变量。
- 不用自然语言模型生成或执行未审查的写请求。
